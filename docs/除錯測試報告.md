# AI 職缺評分管線（Job Scoring Pipeline）除錯與測試報告

**專案：** n8n + Claude API 自動化職缺評分系統
**報告日期：** 2026-06-27

---

## 一、系統架構概述

讀取 Google Sheet 工作底稿中 [狀態] != 完成 的職缺，逐筆走過五個階段，最終依分數門檻決定是否發送通知信：

```
排程觸發(每5分鐘)
  → 讀取待評分職缺列 (Google Sheets)
  → 挑出未完成職缺 (Filter: 狀態≠完成)
  → 設定雙人格評分Prompt與候選人背景 (Set)
  → S1 壓縮JD內容 (Code, Token成本控制)
  → S2 呼叫Claude API評分 (Sonnet 4.6, system block含prompt caching)
  → S3 解析評分結果 (Code)
  → S4 寫回評分結果 (Google Sheets Update)
  → S5 門檻判斷 (Match Score >= 8)
      ├─ true  → 高分職缺通知 (Gmail)
      └─ false → 結束
```

雙人格設計：人格一（鼓勵型生涯教練）找契合點，人格二（嚴格現實派招聘主管）核對必備硬性條件，綜合後輸出單一 match_score。

## 二、除錯歷程（依發現順序）

整個除錯過程是先匯出JSON逐節點核對程式碼與設定，發現問題後請開發者在n8n UI內手動修改、重新匯出驗證，反覆進行。共揪出 8 個跨節點的隱藏問題：

| # | 問題 | 根因 | 修正方式 |
|---|---|---|---|
| 1 | 無法篩選「狀態≠完成」 | Google Sheets節點內建filtersUI只支援「等於」比對，沒有「不等於」選項 | 改為讀取整張表，後面加一個獨立Filter node做notEquals判斷 |
| 2 | JD壓縮結果 original_length 恆為0 | Code node引用的欄位key與Google Sheet實際表頭不一致（有無空格差異：JD內容 vs JD 內容） | 統一Sheet表頭文字與code的key寫法一致 |
| 3 | 多筆資料會被「吃成一筆」 | 「解析評分結果」Code node缺少 `mode: runOnceForEachItem`，預設用Run Once for All Items卻寫的是單筆物件的return寫法 | 補上明確的逐筆執行模式 |
| 4 | 高分職缺亮點(highlight_points)從未寫入Sheet | 寫回節點的欄位mapping中「強調重點」被標記`removed: true`，從未納入實際寫入的欄位清單 | 補上mapping並改回`removed: false` |
| 5 | 通知信內容/主旨有殘留文字與引用不一致 | 信件主旨結尾多出無意義文字，內文引用來源與寫回節點輸出欄位不對應 | 清除殘留文字，統一引用寫法 |
| 6 | 職稱/公司/薪資若用裸$json引用會變成undefined | 「設定雙人格評分Prompt」Set node未啟用Include Other Input Fields，導致除system_prompt外其他欄位在此節點被砍掉 | 將呼叫Claude API節點的引用方式改成直接點名上游節點（`$('讀取待評分職缺列').item.json[...]`），繞過此限制 |
| 7 | 節點Notes內容與實際邏輯不符 | 兩個Google Sheets節點的Notes仍描述已棄用的filtersUI篩選邏輯，未隨#1的修正同步更新 | 重寫成符合現況的說明文字 |
| 8 | fit_note出現「把總年資當成單一程式語言年資」的失真描述 | system_prompt【候選人背景】欄位內仍是當初的範例佔位文字（「請在此填入你自己的真實背景摘要，例如：...」），從未被替換成真實背景，Claude逐字照抄了範例內容 | 依求職者真實履歷重新撰寫候選人背景摘要，並刻意將「總年資」與「特定技術使用年期」拆開敘述，避免模型把不同時間維度混為一談 |

**其中 #2、#6、#8 三個問題的共通模式值得記錄**：表面症狀都是「某個欄位的值不對」，但根因分別是欄位名稱不一致、節點預設行為砍欄位、上游內容本身是佔位文字未替換——同一類症狀，三種完全不同的根因，逐節點追溯資料流向才能正確定位。

UI截圖確認 Minutes Between Triggers = 5，與節點命名「每5分鐘」一致。

### 3.2 機制驗證：idempotency 與多筆item處理

執行畫面顯示：讀取階段3 items進入Filter node，僅1 item被保留（標註"Kept"）繼續往下執行，其餘2筆（狀態已是「完成」的既有測試資料）被正確擋下，未被重複送進Claude API計費評分。證實S0篩選邏輯與#3修正後的逐筆處理機制都實際有效，不只是設定看起來正確。

### 3.3 業務邏輯驗證：true/false 雙分支

### 3.4 候選人背景修正後的重新測試

修正 #8 後，同三筆職缺重新評分，比對結果：

| 職缺 | 修正前分數 | 修正後分數 | 說明 |
|---|---|---|---|
| Odoo ERP軟體工程師 | 8 | **6** | 修正前的8分建立在錯誤的背景描述之上；修正後正確揭露了硬性條件與薪資等方面的落差，分數修正為更準確的6分，屬於評估品質的提升而非退步 |

## 四、目前已知、尚未處理的觀察項

1. **highlight_points 欄位偶有不穩定**：第一輪測試中，Odoo職缺Match Score=8卻未列出強調重點，與system_prompt規則（>=8應列1-3點）不符；後續測試未再復現。判斷屬Claude輸出對自身指令遵循度的機率性誤差，非code層級bug。可選擇加程式防呆（偵測到score>=8但欄位為空時標記人工複查）或接受此風險。

2. **「必備條件」的判定範圍待明文化**：Odoo職缺的部分硬性條件（例如學歷）寫在JD的標準制式欄位（條件要求區），而非JD自行標註的【必備條件】條列區。Claude這次自行判斷將其視為必備並觸發分數上限規則，是合理但目前未明文寫入system_prompt的判斷邏輯，建議補上一句規則明文化，避免依賴模型每次自行解讀。

## 五、結論

本次從第一份匯出的JSON開始，逐節點核對程式碼、欄位引用、節點執行模式、欄位mapping等設定，找出8個跨節點的隱藏問題，並逐一在n8n UI完成修正、重新匯出驗證。最後以真實資料完成端到端測試，包含：idempotency機制驗證、true/false雙分支各自驗證、以及候選人背景品質問題的發現與修正前後對照。整條pipeline目前已確認可正確處理多筆職缺、正確篩選已完成項目、正確雙分支判斷，並驗證過評分品質會隨輸入背景資料的準確度而變化。
